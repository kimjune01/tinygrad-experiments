# CPython JIT Investigation: Why tinygrad's Pattern Matchers Aren't Traced

> **UPDATE (2026-05-08):** This document was written against CPython 3.14. On 3.16.0a0 (recording tracer, gh-139109), the JIT provides -5.8% improvement on optimized builds. The "cascading re-trace" model below is also wrong — `_GUARD_IP__PUSH_FRAME` uses `_COLD_DYNAMIC_EXIT` which does NOT re-trace. See `CPYTHON_JIT_HYPOTHESIS_GRAPH.md` for corrected analysis.

## The mechanism (verified from CPython source)

The JIT CAN trace through function calls — `_PUSH_FRAME` is a traced uop. But it guards the call target with either:
- `_GUARD_IP__PUSH_FRAME`: checks the exact instruction pointer (monomorphic)
- `_GUARD_CODE_VERSION__PUSH_FRAME`: checks the code object version (type-stable)

Both are **monomorphic guards**. They record ONE callee and deoptimize when a different callee appears.

### tinygrad's call pattern

```python
# unified_rewrite loop (traced — it's a hot back-edge)
for _, match, early_reject in pats:   # pats has 9 entries
    match(uop, ctx)                    # different function each iteration!
```

Iteration 0: trace records `match = compiled_match_A`, guards on it → inlines
Iteration 1: `match = compiled_match_B` → **guard fails → side exit**

The trace can never complete a full loop iteration because the callee changes every time. The JIT records a trace of length 1 (one callee), hits the guard on the next iteration, deoptimizes, and falls back to the interpreter.

### The three barriers

1. **Monomorphic call guard**: The JIT guards on the exact callee. Polymorphic dispatch (different function per loop iteration) causes immediate deoptimization.

2. **Frame fitness penalty**: Each `_PUSH_FRAME` charges `fitness_initial / (MAX_ABSTRACT_FRAME_DEPTH - 1)` against the fitness budget. With 16 max depth, each call costs ~1/15 of the total budget. Even if the guard passed, inlining 9 callees would exhaust the budget.

3. **No exec()-specific issue**: The compiled matchers ARE real `PyFunction` objects and pass `PyFunction_Check`. The `co_filename = "<string>"` is only used for debug logging, not filtering. The problem is polymorphism, not code origin.

## What would fix it

### Option A: Polymorphic inline cache (PIC) at call sites

Instead of guarding on one callee, record N most-frequent callees and guard on all of them. V8/HotSpot do this with megamorphic stubs — the guard checks a small cache of known targets.

For tinygrad: the loop calls 9 different functions, but each function is called ~60 times. A PIC of size 9 would cover 100% of calls.

**CPython impact**: Modify `_GUARD_IP__PUSH_FRAME` to check a small table of known IPs instead of one. The table is built during trace recording when the same call site is observed with multiple targets.

### Option B: Trace the loop body WITHOUT inlining callees

Currently the tracer follows `_PUSH_FRAME` into the callee. For polymorphic call sites, it should recognize the polymorphism (guard fails on re-trace) and emit the call as an opaque `_CALL_FUNCTION` uop without inlining. This preserves the loop trace (which IS monomorphic in its non-call operations) and falls back to the interpreter only for the call itself.

**CPython impact**: Add a polymorphism counter per call site. After N guard failures at the same IP, switch from `_GUARD_IP__PUSH_FRAME` to a non-inlining call uop.

### Option C: Aggregate hotness across callees

The 9 compiled matchers are individually cold (~60 calls each). But they share the same code structure (generated by the same `upat_compile`). If the JIT detected that N code objects sharing the same bytecode structure are collectively hot, it could compile ONE template trace that works for all of them.

**CPython impact**: Hash the bytecode (not the code object identity) and aggregate call counts across code objects with the same hash.

## Recommended approach

**Option B is the smallest change with the highest impact.** It doesn't require new data structures (PICs) or new heuristics (aggregate hotness). It just says: "if this call site is polymorphic, don't try to inline it — trace around it." The loop body (early_reject check, return-value check) still gets JIT'd. The callee stays interpreted but is called through a fast path.

The prototype: in `optimizer.c`, when `_PUSH_FRAME` is recorded and the previous trace at this call site had a different callee, emit `_CALL_FUNCTION` instead of `_GUARD_IP__PUSH_FRAME + inline`.
